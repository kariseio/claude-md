## 판단

- 슬럼프가 아니라 구조 문제로 봤다. 병렬 폭, 도메인 전환, 검증 노동, 그리고 분석부터 구현까지 위임하면서 이해를 "만드는" 단계가 생략되고 "읽는" 속도로 요구받게 된 것.
- 핵심은 "요구사항을 잘못 받으면 검증이 무효가 된다"였다. 잘못 받은 요청을 제대로 구현하면 컴파일, 테스트, 로그가 전부 초록인데 결과는 아니다. 검증이 안 되는 게 아니라 검증 대상이 이미 바뀌어 있는 것. 그래서 고치는 지점은 실행 전이어야 한다.
- 기존 전역 CLAUDE.md(8줄)는 "언제 실행하느냐"만 다뤘다. "해줘"가 실행 OK 신호라서 "다 만들어줘"가 그대로 실행됐다. 틀린 게 아니라 한 겹만 있는 것. 실행 OK 신호와 첫 편집 사이에 "무엇으로 이해했느냐"를 붙잡는 층이 빠져 있었다.
- Karpathy 가이드라인을 기반으로 삼되 그대로 쓰지 않았다. 1번(해석이 여럿이면 제시)이 딱 맞는 원칙인데 가장 약했다. "제시하라"지 "멈추라"가 없고, Claude 의 실패 방식은 의심이 안 드는 것이라 원칙은 의심이 들 때만 작동한다. 재진술 게이트는 의심 여부와 무관하게 요청의 형태로 돌린다. "사소한 작업은 판단에 맡긴다"는 탈출구도 뺐다. 그 탈출구가 정확히 오독 39건이 빠져나간 자리다.
- 트리거 단어를 열거하지 않고 insights 리포트의 "Before Answering Ambiguous Requests" 스타일(원칙 문장 + 한국어 예시)로 썼다.
- 본문은 영어, 사용자 입력과 대조하는 문구만 한국어 예시로 남겼다. 오독은 한국어라서 생긴 게 아니라 범위가 빠져서 생긴 것이라, 언어를 바꿔서 얻는 건 토큰 절약이고 오독 방지는 게이트가 한다.
- 저장소는 파일 세 개(CLAUDE.md, README.md, CHANGELOG.md)로 시작했다. 배포 스크립트는 복사 한 줄이라 뺐고, friction-log 는 `/insights` 가 이미 하는 일이라 뺐다. README 는 GitHub 의 다른 CLAUDE.md 저장소들 구조를 조사해서 맞췄고, 내 상황 설명은 빼고 각 섹션의 목적만 남겼다.

## 느낀 점

- 슬럼프라고 느꼈다. 이해가 느려지고, 코드를 확인해야 하는데 속도가 안 나고, 머리가 자꾸 꼬였다. 리포트를 보고 나서는 능력 문제라기보다 구조 문제로 보게 됐다. 병렬 폭, 다섯 개 도메인, 그리고 하는 일의 대부분이 작성이 아니라 검증이었다는 것.
- 요구사항을 자꾸 잘못 받으니까 검증이 제대로 안 되는 느낌이었다. 신호는 전부 초록인데 결과가 아닌 상태. 검증이 안 되는 게 아니라 검증 대상이 이미 바뀌어 있었다.
- 내 프롬프트가 잘못됐을 수도 있다고 생각했다. 짚인 건 네 가지. 목적어에 대상이 없음("X 추가"), 제약이 작업 뒤에 옴, 교정에 정답이 없음("아니야 있어"), 이전 세션을 "다", "그거"로 부름. 첫째와 넷째는 게이트가 흡수한다. 제약을 요청 첫 줄에 두는 것과 교정 뒤에 정답 한 줄을 붙이는 건 내 습관이다.
